# The Generated Error Model

## 1. Why this chapter exists

The SDK throws one error type, `ZcashError`, across every public surface. Two
of the three files that define it are generated and carry a `DO NOT EDIT`
banner. If you add a case to the generated file by hand, the next regeneration
silently overwrites it, and your error disappears. This chapter explains the
three-file pipeline (`ZcashErrorCodeDefinition.swift` is the source;
`ZcashError.swift` and `ZcashErrorCode.swift` are generated by Sourcery), the
error-code format, and the invariant that keeps the codes unique. By the end
you will be able to add a new error case correctly and explain why the test
suite catches a duplicate code at build time.

## 2. Definitions

**Definition 17.1 (ZcashError).** `ZcashError` is the public, associated-value
enum thrown throughout the SDK. Each case carries the context needed to
diagnose the failure (a wrapped `Error`, a URL, a rust-layer message string,
etc.). It is declared `public enum ZcashError: Equatable, Error`.

**Definition 17.2 (ZcashErrorCode).** `ZcashErrorCode` is a flat
`String`-backed enum with one case per `ZcashError` case and no associated
values. Its raw value is the stable error code string. It exists so a caller
can switch on or log the code without destructuring the associated values.

**Definition 17.3 (the code format).** Each code starts with `Z`, then 0-4
letters naming the SDK area, then four digits. Examples: `ZSRVC0002`
(LightWalletService getInfo), `ZRUST0002` (rust createToAddress), `ZINIT0001`
(Initializer alias). The format and the uniqueness requirement are stated in
the header comment of the definition file
([`ZcashErrorCodeDefinition.swift` lines 19-24](https://github.com/zcash/zcash-swift-wallet-sdk/blob/fe836893bc71fc3e6eb173f4fc191aa43c3760af/Sources/ZcashLightClientKit/Error/ZcashErrorCodeDefinition.swift#L19-L24)).

**Definition 17.4 (the generation pipeline).** The flow is: edit
`ZcashErrorCodeDefinition.swift` (add a `case` with a `// sourcery: code="..."`
annotation and a `///` doc comment) -> run
`Error/Sourcery/generateErrorCode.sh` with Sourcery installed -> Sourcery reads
the definition plus the two `.stencil` templates and rewrites
`ZcashError.swift` and `ZcashErrorCode.swift`.

**Invariant 17.5 (never hand-edit the generated files).** `ZcashError.swift`
and `ZcashErrorCode.swift` both begin with `DO NOT EDIT` and instruct you to
edit the definition file instead. Manual edits are lost on the next run of the
script.

**Invariant 17.6 (codes are unique).** Every code in the definition file must
be unique. The header comment states that `ZcashErrorCode` is generated from
these codes, so a duplicate produces two enum cases with the same raw value and
the generated file fails to compile.

## 3. The code

### The source of truth: the definition file

`ZcashErrorCodeDefinition.swift` is the only file you edit. Its header comment
states the rules: the enum is never used directly in code, `///` is for
documentation (the first line becomes the generated `message`), and `//
sourcery:` carries the code annotation.

```swift reference title="Sources/ZcashLightClientKit/Error/ZcashErrorCodeDefinition.swift"
https://github.com/zcash/zcash-swift-wallet-sdk/blob/fe836893bc71fc3e6eb173f4fc191aa43c3760af/Sources/ZcashLightClientKit/Error/ZcashErrorCodeDefinition.swift#L12-L24
```

A single case looks like this. The `///` line is the human-readable message;
the `// sourcery: code=` line is the stable code; the `case` declares the
associated values.

```swift reference title="Sources/ZcashLightClientKit/Error/ZcashErrorCodeDefinition.swift"
https://github.com/zcash/zcash-swift-wallet-sdk/blob/fe836893bc71fc3e6eb173f4fc191aa43c3760af/Sources/ZcashLightClientKit/Error/ZcashErrorCodeDefinition.swift#L171-L174
```

### The generated enum: ZcashError

Sourcery copies the `///` doc and the code into a single `///`-comment block,
then emits the same `case`. Note the `DO NOT EDIT` banner.

```swift reference title="Sources/ZcashLightClientKit/Error/ZcashError.swift"
https://github.com/zcash/zcash-swift-wallet-sdk/blob/fe836893bc71fc3e6eb173f4fc191aa43c3760af/Sources/ZcashLightClientKit/Error/ZcashError.swift#L1-L9
```

The `rustCreateToAddress` case is generated from the definition above. The code
moved from the `// sourcery:` annotation into the `///` block; the `case` line
is identical to the definition.

The same template also generates a `message` property (the first `///` line of
each definition case) and a `code` property (mapping each case to its
`ZcashErrorCode`). For `rustCreateToAddress` these two generated lines are:

`ZcashError` also conforms to `LocalizedError`, with `errorDescription`
formatted as `"<code>: <message>"`. This is what a caller sees in
`localizedDescription`.


### The generated code enum: ZcashErrorCode

The second template emits the flat `String`-backed enum. The raw value is the
code from the definition. For `rustCreateToAddress`:

```swift reference title="Sources/ZcashLightClientKit/Error/ZcashErrorCode.swift"
https://github.com/zcash/zcash-swift-wallet-sdk/blob/fe836893bc71fc3e6eb173f4fc191aa43c3760af/Sources/ZcashLightClientKit/Error/ZcashErrorCode.swift#L85-L85
```

So one definition case (`ZRUST0002` / `rustCreateToAddress`) produces three
generated artifacts that must agree: the `case` in `ZcashError.swift`
(line 140), the `.code` mapping (line 1032), and the `ZcashErrorCode` raw value
(line 85). The chain of equalities the worked example shows is: definition
annotation `code="ZRUST0002"` -> `ZcashErrorCode.rustCreateToAddress =
"ZRUST0002"` -> `ZcashError.rustCreateToAddress.code == .rustCreateToAddress`.

### The generator script

`generateErrorCode.sh` runs Sourcery twice, once per template, writing the two
output files into the parent `Error/` directory. It checks the installed
Sourcery version against a pin.

```bash reference title="Sources/ZcashLightClientKit/Error/Sourcery/generateErrorCode.sh"
https://github.com/zcash/zcash-swift-wallet-sdk/blob/fe836893bc71fc3e6eb173f4fc191aa43c3760af/Sources/ZcashLightClientKit/Error/Sourcery/generateErrorCode.sh#L1-L34
```

Two branches matter here:

- Precondition: `sourcery` is on `PATH` and its `--version` equals
  `2.3.0` (lines 6-12). The script `exit 1`s with a warning if the version does
  not match exactly. This is the same pin the test-mock script uses; see
  `CLAUDE.md`, which records Sourcery 2.3.0 as the hard requirement for the
  mock generator.
- Fallback: if `sourcery` is not installed at all, the script only prints a
  warning and does not regenerate (lines 32-34).

Note: the version check at line 9 is a string equality on the full
`sourcery --version` output. The pinned value is `2.3.0` (line 6).

## 4. Failure modes

- Hand-editing `ZcashError.swift` or `ZcashErrorCode.swift`: your change is
  overwritten the next time anyone runs `generateErrorCode.sh`, because both
  files are regenerated wholesale from the definition (see the `DO NOT EDIT`
  banner at [`ZcashError.swift` lines 1-9](https://github.com/zcash/zcash-swift-wallet-sdk/blob/fe836893bc71fc3e6eb173f4fc191aa43c3760af/Sources/ZcashLightClientKit/Error/ZcashError.swift#L1-L9)).
  No automated test in this workspace; caught by audit only (the loss is silent
  until the next regeneration).
- Adding a case to `ZcashErrorCodeDefinition.swift` without rerunning Sourcery:
  the new case never appears in `ZcashError` or `ZcashErrorCode`, so code that
  references it does not compile, or the error simply cannot be thrown. Caught
  by: the project build (the referencing call site fails to compile against the
  un-regenerated `ZcashError`).
- Duplicate code (two definition cases with the same `code="..."`): the
  generated `ZcashErrorCode` enum has two cases with the same raw `String`
  value and fails to compile, per Invariant 17.6 and the header comment at
  [`ZcashErrorCodeDefinition.swift` lines 19-24](https://github.com/zcash/zcash-swift-wallet-sdk/blob/fe836893bc71fc3e6eb173f4fc191aa43c3760af/Sources/ZcashLightClientKit/Error/ZcashErrorCodeDefinition.swift#L19-L24).
  Caught by: the project build of the regenerated file.
- Changing the `errorDescription` format or a code value without updating
  callers that string-match on it: `ZcashErrorLocalizedTests` asserts the exact
  format `"ZRUST0002: Error from rust layer when calling
ZcashRustBackend.createToAddress"` and that `localizedDescription` contains
  the code. Caught by: `Tests/OfflineTests/ZcashErrorLocalizedTests.swift`
  (`testLocalizedDescriptionFormat`, `testErrorCodeProperty`).

## 5. Spec pointers

- Sourcery (https://github.com/krzysztofzablocki/Sourcery): the code generator
  that reads `ZcashErrorCodeDefinition.swift` and the `.stencil` templates. The
  version pin (2.3.0) in `generateErrorCode.sh` line 6 must match the installed
  binary or the script aborts.
- `CLAUDE.md` (repo root), "Generated code" section: lists the three kinds of
  generated code in this repo and states that the test-mock generator hard-
  checks Sourcery 2.3.0; the error-code generator uses the same pin.
- See [the Swift<->Rust bridge](./04-swift-rust-bridge.md): rust-layer failures
  cross the FFI boundary as a message string and are wrapped into `ZcashError`
  cases such as `rustCreateToAddress(_ rustError: String)`.
- See [the build, test, and contribution loop](./02-build-test-contribution-loop.md):
  the regeneration step (run Sourcery, commit the regenerated files) is part of
  the contribution workflow whenever you touch the error definition.

## 6. Exercises

1. Match a definition case to its generated artifacts. Pick the
   `serviceGetInfoFailed` error. Find (a) its definition `case` with the
   `// sourcery: code=` line in `ZcashErrorCodeDefinition.swift`, (b) its
   generated `case` in `ZcashError.swift`, and (c) its raw value in
   `ZcashErrorCode.swift`. State the code string and confirm all three agree.

2. Read `Tests/OfflineTests/ZcashErrorLocalizedTests.swift`. Which test asserts
   the exact full `localizedDescription` string for a `ZcashError`, and what is
   the expected string? Which test asserts that an `NSError` bridge does not
   show the opaque ordinal form (e.g. `error 29`)?

3. Modify (describe only, do not run Sourcery). Add a new error case to
   `ZcashErrorCodeDefinition.swift`, for example a hypothetical
   `checkpointUnsupportedNetwork(_ network: String)`. Write the exact three
   lines you would add (the `///` doc, the `// sourcery: code="ZCHKP000N"`
   annotation with an unused code, and the `case`). Then state the single
   command a contributor must run next, and name the two files it regenerates.
   Explain why simply adding the lines and committing is not enough.
